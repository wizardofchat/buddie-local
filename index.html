§ 0 — Abstract

The Existence Proof

Buddie.local is a live, privately built personal agent system. It started on a Samsung A55 phone running Termux on 25 February 2026 and now runs on a home Mini PC in the UK. Built entirely outside working hours on personal hardware.

It stores personal finance, health and energy data locally in PostgreSQL. An Android companion app reads its REST API. Scheduled agents fetch data, write reports and produce daily observations. Since the first version of this paper in May 2026, both main data providers have changed, and the system has gained a second kind of agent: ones that run from a written mission file, and one that turns a GitHub issue into a pull request.

This revision removes or corrects every claim in the May paper that the system's own logs do not support. Where something is planned, it says planned.

This paper documents the architecture, what actually runs, what is measured and what is not, and the limitations. It is an existence proof that one person can build and run this on hardware they already own. It is not a claim that the system is finished, accurate or private in every respect.

§ 1 — Architecture

Governor, not model. Deterministic first, LLM last.

The central design is a governor layer that routes every query to the cheapest capable tier. Every query passes through five steps: understand intent → audit data freshness → extract surgical context → route to tier → log everything.

That query path is the May design. It has not been re-verified for this revision and it is barely exercised: 7 questions in the 30 days to 15 Nov 2026. The work since May has gone into scheduled agents, imports and reports, which is where the rest of this paper spends its time.

Two ways data arrives

The finance pipeline reads from a live broker API or from files a person drops in. Until autumn 2026 holdings came from Trading 212 over its API. That account is being phased out; holdings now come from Interactive Investor, which has no API, as a monthly CSV export. Bank statements arrive the same way. Prices and valuation run as their own daily jobs, so the portfolio value no longer depends on any broker being reachable.

The health pipeline changed too. Whoop has been replaced by a daily Garmin job as the primary source, with Android Health Connect records arriving through a small companion app as a second source. Both feed the same health views, so the rest of the system did not need to know the device changed.

§ 2 — Agents

Scheduled agents. Each with one job.

Every agent runs on a systemd timer and reports to an agent_runs table. Each fails independently. One caveat belongs here and not in the small print: "success" in that table currently means the process exited cleanly, not that it did useful work.

From issue to pull request — the coding agent

The May paper described a /prompt → /code self-extension pipeline. This flow supersedes it. The agent never decides what to build and never merges its own work.

issue
A GitHub issue in a fixed shape — goal, files, what must not change, and what "done" means
label
A person marks it ready — nothing starts without that, and only one issue is in flight at a time
write
The agent writes the change — within an allowed set of paths, under a monthly spend cap
test
Tests run in a sandbox with no network access
PR
Pull request opened — a person reviews and merges. Never the agent.

State on 15 Nov 2026: 13 runs in the previous 7 days, 12 completed, and two clean pull requests merged so far. That is a small sample, not a track record.

§ 3 — Daily Synthesis

Observations every morning. Most of them never shown.

Synthesis agents for finance, health and energy run every day, followed by a cross-domain pass. Each reads shaped data and writes structured observations with a confidence score. Nothing acts on them: the system runs in ghost mode with autonomous writes switched off in configuration.

Which model sees what

The scheduled health synthesis runs on a local model on the same machine, and the health reports are computed locally. Other features that read health data, such as the council and proactive alerts, have not yet been audited for which model they use. Finance and energy synthesis are sent to a cloud model (Claude Haiku, through OpenRouter), with a hard cost cap per run. Until November 2026 health synthesis used the cloud model too, which contradicted the rule this system was built on. That has been corrected.

The May paper said tickers were anonymised before any cloud call. An anonymisation step exists, but it has not been verified end to end, so that claim is withdrawn until it is.

What the numbers say about the feedback loop

The May paper presented ratings as a working calibration loop. Measured on 15 Nov 2026, it is not one.

A rating history with no "wrong" in it carries no information. The honest reading is that the system produces far more observations than one person will read, and the next step is fewer of them, not a better score for each.

Trust architecture

01
No model may both generate and authorize the same action. This is a design rule. Today it holds mostly because nothing acts on observations at all; the separate verification step is not active.
02
Observations are not recommendations. "What happened?" is automatic. "What should you do?" stays with the person. No synthesis output triggers an action.
03
Storage is local. Model use is stated, not implied. Health synthesis runs on a local model. Finance and energy synthesis use a cloud model. The May claim that this was "enforced by architecture" was wrong: it is a configuration setting, and until November 2026 it pointed health synthesis at a cloud model.
04
Confidence has not been earned yet. Confidence scores are uncalibrated, and the ratings that were meant to calibrate them do not. Nothing unlocks on them.
§ 3.5 — Paper Trading

Paper trading. No real orders.

A paper-trading agent runs every morning against a fixed paper budget. It has never placed a real order. The May paper described real execution as ready and waiting on trust; with the move to a broker that has no trading API, automated execution through the broker is no longer possible, and this paper drops the claim.

§ 3.6 — Two Loops

Two loops. One verified, one not re-measured.

The May paper described two autonomous loops with a detailed diagram. The diagram named components and counts that no longer match the system, so it has been removed. What can be said today:

Loop 1 — Paper Trade

Select, record, check the outcome

Runs daily and opens paper trades, as described in § 3.5. Outcome records exist. Whether those outcomes change later selections in a way that improves them has not been measured.

Loop 2 — Market Correlation

Project, then validate

The projection and validation jobs still run on their timers. Their accuracy has not been re-measured for this revision, so no accuracy figure is given.

A loop is only closed when the measurement at the end changes what happens at the start.

By that test, neither loop is proven closed today. Both run. That is the accurate claim.

§ 4 — VitaNest

Kindle-inspired. Intelligence without noise.

VitaNest is a Kotlin/Jetpack Compose Android app consuming the backend's REST API. It follows a Kindle-inspired minimalist design language — cream backgrounds, near-black serif typography, no colour except where it carries meaning. No engagement mechanics. Designed to inform, not to retain.

VitaNest contains zero business logic. No calculations, no hardcoded values, no data storage. The backend is the brain; VitaNest is the window. That boundary held when the health source changed in October 2026: the app's health screens were pointed at the new health views without the app needing to know which device the data came from.

Portfolio lens — risk classification

Every holding is classified across four dimensions: currency exposure, geography, income type and asset class. The lens screen surfaces concentration risk, currency drag and income distribution without manual tagging.

§ 6 — The Opportunity

Why local-first personal finance intelligence matters.

Retail investors in the UK, India and elsewhere hand their most sensitive financial data to platforms they do not own and cannot audit, and get back tools that forget their decisions between sessions.

The aim: your data on your machine, and model use you can see.

Buddie.local's aim is the inverse of the usual arrangement: data stored on hardware you own, a permanent record of your own decisions, and cloud models used only where you choose and can see.

This revision shows that aim is not fully met yet, and says exactly where. Publishing that is the point.

The architecture is broker-agnostic, and in 2026 that stopped being a slogan. The broker changed from one with a live API to one with only a monthly CSV export, and the import layer reads either. The migration is still in progress (see Limitations). The same pattern should work for any broker that offers an API or a file export; so far it has been tried with exactly two.

§ 9 — Honest Limitations

What this is not. What still needs building.

A credible architecture document acknowledges its boundaries clearly. This list is longer than it was in May because more was checked.

Current limitations

Single-user personal system. Not productised, multi-tenant, or production-hardened for regulated financial services.
Health synthesis ran through a cloud model until November 2026, contrary to the system's own rule. It now runs on a local model. That is a configuration setting, not an architectural guarantee, and nothing yet tests that it stays that way.
Finance and energy synthesis are sent to a cloud model. Whether tickers are anonymised in everything that is sent has not been verified.
Other features read health data to answer a question or raise an alert, including the council and the proactive alerts. Which model each of them uses has not been audited yet, so health data staying local is only established for the scheduled synthesis and the reports.
The feedback loop does not work as a loop. In 90 days: 301 observations rated useful, none rated wrong or important, 1,835 unrated. Three quarters of observations are stored hidden.
Almost nobody asks it questions: 7 in 30 days. The question-answering path described in § 1 is the least-used part of the system.
Agent "success" means the process exited cleanly. Jobs for providers that are being retired still run and still report success.
The broker migration is unfinished. One holdings snapshot has been imported from the new broker so far, and both sources are still configured.
With no API at the new broker, holdings are at most as fresh as the last monthly export. No real-time market data feed.
Tests exist (81 functions) but nothing runs them automatically. There is no CI.
Backups run nightly to the same machine. No restore drill has been recorded since August 2026, and an off-machine copy is not routine.
Confidence scores are uncalibrated.
Paper trading: the candidate universe needs re-basing after the broker change, and one retired rule is not confirmed removed.
Single machine, CPU only. Local models take tens of seconds per answer.
Internal architecture documents predate the changes in this revision and are being rewritten.
Earlier self-assigned readiness scores have been retired. They were asserted, not derived.
FCA regulatory boundary: this system produces observations and decision support, not regulated financial advice.
The main code repository is private. The source of this paper is public.
